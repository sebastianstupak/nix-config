# Secrets (sops-nix)

Encrypted secrets live here. **Only ciphertext is committed** — sops-nix decrypts
at activation time into `/run/secrets/<name>` (root-readable, or as configured).
Cloning this repo yields nothing but encrypted blobs.

The plumbing is wired (`sops-nix` input in `flake.nix`, `sops.age.sshKeyPaths`
in `modules/nixos/core.nix`, `.sops.yaml` at the repo root). Files are laid out
by who may read them:

```
secrets/common/      every machine + you   calendars.yaml, backup.yaml, passwords.yaml
secrets/zagreus/ that machine + you    (empty until you split the password)
secrets/hestia/     that machine + you    (empty until you split the password)
```

`secrets/common/` has to stay readable by every machine — the restic
credentials are used by all of them. A host directory deliberately excludes the
other machines, so a stolen laptop can read the hash it already had to have and
not the other's.

> **The login password comes from here.** `sebastianstupak-hash` in
> `passwords.yaml` feeds `users.users.sebastianstupak.hashedPasswordFile`, and
> `users.mutableUsers = false`. If a machine cannot decrypt this file it cannot
> log in at all — see "The lockout" below before installing or reinstalling.

## 1. Recipient keys (already registered)

`.sops.yaml` encrypts every secret to **three** age recipients, and all are
needed:

| recipient | source | why |
| --- | --- | --- |
| `zagreus` | host key `/etc/ssh/ssh_host_ed25519_key` on the AMD HP laptop | sops-nix decrypts as root at activation (`sops.age.sshKeyPaths`, `modules/nixos/core.nix`). Without it the machine cannot read its own secrets at boot. |
| `hestia` | host key of the Intel machine (SK hynix PC801) | same mechanism, different host key. Was called `workstation_intel` while it booted `hosts/zagreus/`; renamed when it got `hosts/hestia/`. The key material did not change — the anchor is just a name. |
| `sebastianstupak` | standalone age key `~/.config/sops/age/keys.txt` | `sops` runs as you and cannot read the root-owned host key. Without it you could create a secret and never reopen it. |

### The lockout

A host key is **regenerated by every reinstall**, which silently invalidates that
machine's recipient. The failure mode is not a warning you can ignore:

1. sops-nix cannot decrypt, so `/run/secrets-for-users/sebastianstupak-hash`
   never appears.
2. `hashedPasswordFile` points at a missing file. `update-users-groups.pl` only
   warns about that — it leaves `hashedPassword` undefined.
3. With `mutableUsers = false`, line 299 of that script writes `"!"` into the
   shadow entry **unconditionally**, and line 300 only restores a real hash if
   one is defined. Both `sebastianstupak` and `root` end up locked.
4. This runs on *every activation*, which includes every boot — so fixing it
   with `passwd` from a rescue chroot works until you reboot, then reverts.

So when installing or reinstalling a machine, enrol its host key **before the
first boot**: generate the key into the target at
`/mnt/etc/ssh/ssh_host_ed25519_key`, derive the recipient, add it here, and run
`sops updatekeys` on every file. `docs/INSTALL.md` step 6 does exactly this.

Recovering from it needs a rescue boot plus an actual `nixos-rebuild` (either
enrolling the key properly, or temporarily setting `mutableUsers = true` so
`passwd` survives activation). `passwd` alone can never fix it.

The user recipient is a standalone age key rather than one derived from
`~/.ssh/id_ed25519`: that key is passphrase-protected, and `ssh-to-age` has no
passphrase support, so an ssh-derived recipient would encrypt to something
nothing can decrypt. sops cannot consume the ssh key as an age identity either.

`~/.config/sops/age/keys.txt` is **not** in this repo and is not reproducible —
it is machine-local secret material, mode 600. It is THE thing to keep in the
password manager — see "What to keep OUTSIDE these machines" below. Lose it and
you can still decrypt via a host key with `sudo`; lose it and the machines and
the secrets are gone. Regenerate a replacement with `age-keygen`, then update
`.sops.yaml` and run `sops updatekeys secrets/<file>`.

To re-derive the values:

```bash
nix run nixpkgs#ssh-to-age -- -i /etc/ssh/ssh_host_ed25519_key.pub  # host
grep 'public key' ~/.config/sops/age/keys.txt                       # user
```

## What to keep OUTSIDE these machines — one key, nothing else

**There is exactly one thing to store in the password manager: your age key.**
Everything else either lives inside sops (so that key recovers it) or can be
regenerated. If the list ever grows past one item, something has gone wrong.

That is not a simplification of a complicated scheme; it is how it already
works. Each machine decrypts with its own SSH host key, derived to an age
identity by sops-nix — that is the one key per device, and it never leaves the
device. Your personal age key is the human equivalent, and it is the only one
that has to survive the machines.

### The one item

**`nixcfg/age-key`** — a Proton Pass **secure note** (it is multi-line; login
items mangle that).

```bash
wl-copy --sensitive < ~/.config/sops/age/keys.txt
```

`--sensitive` is not optional: a `wl-paste --watch cliphist store` daemon runs
on these machines and its database is world-readable, so anything copied
without the hint is logged in plaintext for every local process to read.
Afterwards:

```bash
wl-copy --clear
cliphist list | head        # nothing secret should appear; `cliphist wipe` if it does
```

### Restoring it on a new or rebuilt machine

```bash
mkdir -p ~/.config/sops/age
# paste the note from Proton Pass:
wl-paste > ~/.config/sops/age/keys.txt      # or: $EDITOR ~/.config/sops/age/keys.txt
chmod 600 ~/.config/sops/age/keys.txt

# prove it before relying on it
sops -d secrets/common/backup.yaml >/dev/null && echo "age key works"
```

Faster than that, and it names the expected value instead of just failing:

```bash
bash scripts/check-age-key.sh
```

### Which copy is authoritative

The private half deliberately exists in several places — the Proton Pass note
and every machine you edit secrets from. That is what makes it survivable, and
it is also the one real hazard: **several copies of one logical key can
silently diverge.**

**`.sops.yaml` is the source of truth.** Its `&sebastianstupak` anchor is the
public half every secret here is encrypted to; a key on disk is correct if and
only if it derives to that value. There is no second opinion to consult, and a
key sitting at the documented path with the documented permissions is not
evidence of anything.

So when a machine cannot decrypt, **replace the key, never the anchor.** The
files on disk are already encrypted to the anchor. Editing the anchor to match
a stray key requires `sops updatekeys` on every file and re-keys the repo to
whatever that machine happens to hold — which is how you lose the escape hatch
rather than repair it.

`scripts/check-age-key.sh` enforces this, and lefthook runs it on any commit
touching `secrets/` or `.sops.yaml`. A missing key skips (a host that never
edits secrets does not need one, and decrypts its own at activation with its
host key); a key that is present and *wrong* fails the commit. That is the
case worth catching, because it is the one that looks fine:

- **2026-11-01** — the anchor had drifted from the key in use, so every file was
  encrypted to a recipient that existed nowhere. The machines never noticed;
  only the human escape hatch was dead.
- **2026-11-03** — zagreus held a *third* key from 2026-09-10 that was a
  recipient of nothing. Recovered by copying hestia's working key over the
  overlay after comparing public halves, which is usually quicker than the
  Proton Pass route and verifiable before you overwrite anything.

### What it recovers

Everything in `secrets/`, which is to say everything that matters:

```bash
sops -d --extract '["restic-password"]' secrets/common/backup.yaml   # restore backups
sops -d --extract '["restic-env"]'      secrets/common/backup.yaml
sops -d --extract '["setup-key"]'       secrets/common/netbird.yaml  # rejoin the VPN
sops -d --extract '["work-url"]'        secrets/common/calendars.yaml
```

### The two things that must both survive

The age key is half of it. The other half is **this repository on GitHub** —
it holds the encrypted files the key opens. Neither is useful alone, so:

- keep the key in Proton Pass, not on a machine, and
- **push.** Unpushed changes to `secrets/` are the failure mode that looks
  fine until it is not: the remote keeps an older ciphertext, and after a
  re-key that older copy may be encrypted to recipients that no longer exist.

### Deliberately NOT stored

- **restic password, restic S3 env, netbird setup key** — all inside sops. The
  age key already recovers them; a second copy is a second thing to rotate and
  forget.
- **Sunshine web UI password** — reset it with `sunshine --creds <user> <pass>`,
  then restart the unit so the running process reloads them.

  **Do NOT delete `~/.config/sunshine/sunshine_state.json`**, which this file
  used to recommend. Credentials are not the only thing in it: every paired
  client lives there too, under `root.named_devices`. Deleting it silently
  unpairs every device and each one has to be PIN-paired again, which needs
  the web UI you were trying to get back into. `--creds` rewrites only the
  credential fields and leaves the pairings intact.

  Worth recording per host rather than relying on regeneration — hestia's was
  not, and on 2026-11-03 that blocked pairing zagreus to it, because the PIN
  for a pairing is entered in the web UI of the machine being streamed FROM.
  So a forgotten password on one host blocks exactly the direction that host
  serves.
- **SSH key passphrase** — if lost, generate a new keypair and update
  `my.remote.authorizedKeys`. The key is a credential, not an archive.

### The one genuine gap: your login password

`passwords.yaml` holds only the **hash**, because that is what NixOS consumes
— so the plaintext exists nowhere, and it is also your VNC password (wayvnc
authenticates through PAM). Losing it means resetting from a recovery boot.

Close the gap by putting the plaintext beside the hash, which makes the age
key sufficient for this too:

```bash
sops secrets/common/passwords.yaml
# add alongside the existing hash:
#   sebastianstupak-password: <the plaintext>
```

Nothing in Nix reads that value — `hashedPasswordFile` still points at the
hash. It is there so a human with the age key can recover it. The trade is
that a sops compromise yields the login password as well as the hash; given
the same file set already yields the restic credentials and the VPN setup
key, the blast radius does not meaningfully change.

## Splitting a host's password

Both hosts currently point `sebastianstupak-hash` at
`secrets/common/passwords.yaml`, so both machines share one password. The
layout and the `.sops.yaml` rules for a per-host file are already in place; the
split is two steps per machine, and **the order matters** because the halfway
state is the lockout below.

Do this ON the machine being split, so its host key is available to verify
with:

```bash
# 1. Create the file. The creation rule encrypts it to THIS host and to you,
#    and to nothing else.
sops secrets/hestia/passwords.yaml          # or secrets/zagreus/...

#    Put a hash in it, generated however you like:
#      mkpasswd -m yescrypt
#    as:  sebastianstupak-hash: $y$j9T$...

# 2. PROVE you can read it back before anything depends on it. If this fails,
#    stop — repointing the host now would lock you out on the next activation.
sops -d secrets/hestia/passwords.yaml
sudo nix run nixpkgs#sops -- -d secrets/hestia/passwords.yaml   # as root, via the host key

# 3. Only then repoint the host and rebuild.
#      hosts/hestia/default.nix:  sopsFile = ../../secrets/hestia/passwords.yaml;
git add -A
nixos-rebuild build --flake .#hestia
sudo nixos-rebuild switch --flake .#hestia
```

Keep a rollback target handy: `sudo nixos-rebuild switch --rollback` restores
the previous generation, and the boot menu holds 20 of them.

Once both hosts have their own file, `secrets/common/passwords.yaml` has no
reader and should be removed.

## 2. Create an encrypted file

```bash
sops secrets/secrets.yaml
```

Your `$EDITOR` opens on decrypted content; sops re-encrypts on save. Add e.g.:

```yaml
example_token: super-secret-value
```

## 3. Declare the secret in Nix

In a module (or the host config):

```nix
sops.secrets."example_token" = {
  sopsFile = ../../secrets/secrets.yaml;
  # owner = "sebastianstupak"; mode = "0400"; etc.
};
```

Reference the decrypted path at runtime via
`config.sops.secrets."example_token".path` (→ `/run/secrets/example_token`).

## Rules

- **Never** commit plaintext. Only edit secret files through `sops`.
- `git add` the encrypted file before you rebuild (see the repo `AGENTS.md`).
- If you rotate/add recipients, run `sops updatekeys secrets/<path>.yaml`.
- Moving a file between `common/` and a host directory does **not** re-encrypt
  it. The creation rules only apply to new files and to `sops updatekeys`, so
  run that afterwards or the file keeps its old recipients — more permissive
  than the directory implies.
